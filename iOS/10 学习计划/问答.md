# iOS 底层问答

## 进程内存与地址空间

### 虚拟内存、页面与内存

#### 虚拟内存和物理内存有什么区别？

虚拟内存是操作系统提供给每个进程的一套独立地址空间。App 里的指针首先是虚拟地址；CPU 访问时，MMU 根据页表把虚拟页转换到物理页，并检查读、写、执行权限。物理内存则是设备真实存在的 RAM。

建立虚拟地址映射，不等于立刻占用同等大小的物理内存。页面可以等到第一次真正访问时，再通过 Page Fault 获得物理支持。Page Fault 本身也不一定是错误：如果映射合法，内核可以载入文件内容、分配零填充页或完成 Copy-on-Write，然后让原指令继续执行；只有地址未映射或权限不允许且无法修复时，才可能出现 `EXC_BAD_ACCESS`。

#### `malloc` 申请了多少内存，Memory Footprint 就会立即增加多少吗？

不会。`malloc` 返回一段可用地址，与页面真正形成 App 的内存责任是两个动作。分配器可能从已有 Region 中分出空间，也可能复用已经存在的页面。程序首次触碰页面时，系统才按需建立物理支持；实际写入以后，页面才可能变成 dirty page。

文章在 16 KiB 页面设备上的实验中，`malloc(32 KiB)` 后 Footprint 没有立即增加 32 KiB。首次写入后的变化也不能机械归纳为“写一个字节必然增加一页”，因为分配器复用、页对齐、采样精度和进程内其他活动都会影响结果。

```text
申请或映射虚拟地址
        ↓
首次访问，页面获得物理支持
        ↓
写入页面，可能形成 Dirty Memory
        ↓
Dirty / Compressed 推高 Memory Footprint
```

#### Clean、Dirty 和 Compressed Memory 分别是什么？

Clean 表示页面内容可以从原始来源重新取得，例如尚未修改的可执行文件、Framework 代码页和只读文件映射。Clean 不等于“没有占用 RAM”，也不等于“页面不可写”；访问权限和页面内容是否可重建是两个维度。内存压力下，系统可以丢弃可重建的 clean page，需要时再加载。

Dirty 表示页面内容已经被修改，不能在不保存内容的情况下直接丢弃。实际写入的堆对象、解码后的图片缓冲区、可变集合、缓存和 Copy-on-Write 形成的私有页面都可能成为 dirty memory。`malloc` 过但没有触碰的整段地址，不能直接等同于 dirty memory。

Compressed 是系统把近期不活跃、又不能直接丢弃的页面压缩后继续保存。压缩后的实际存储可能更小，但内容仍然属于 App 的内存责任；Footprint 对 compressed dirty memory 按压缩前的原始大小记账。重新访问还需要解压，因此压缩也会带来 CPU 和能耗成本。

```text
文件支持的 Clean Page
        ↓ 首次写入触发 Copy-on-Write
进程私有的 Dirty Page
        ↓ 内存压力
Compressed Page
```

#### `virtual_size`、`resident_size` 和 Memory Footprint 有什么区别？

- `virtual_size`：进程建立或保留了多大的虚拟地址范围，不代表占用了同等大小的 RAM。
- `resident_size`：当前有多少进程页面驻留在物理内存中，其中可能包含可重新加载的 clean page。
- `TASK_VM_INFO.phys_footprint`：更接近系统为该进程记录的责任内存，也是理解 Xcode Memory Gauge 时更有价值的指标。

#### 64 位指针是否意味着 App 拥有 \(2^{64}\) 字节可用地址空间？

在 iPhone 15 未启用 Extended Virtual Addressing entitlement 的实验中观察到：指针为 64 位，但普通 task 的实测页级上界约为 17.375 GiB，最大连续可保留空洞约为 5.375 GiB。`task_vm_info.virtual_size` 中还包含 GPU carveout 等特殊保留区，不能解释成 App 可自由使用的内存。

即使成功保留数 GiB 虚拟地址，也不等于可以安全写入同等大小的物理内存；一旦逐页触碰，问题就从“能否保留地址”变成“系统能否提供物理页、Footprint 是否越限”。

Extended Virtual Addressing entitlement 只表示系统允许 App 访问扩展地址空间。具体上限随设备、系统与内核实现变化，也不意味着 RAM、Memory Footprint 或 Jetsam 限制同步提高。

### 进程内存布局、VM Region 与 Mach-O

#### “内存五大分区”与真实的 iOS 进程内存地图是什么关系？

代码区、常量区、全局/静态区、堆、栈

- 代码、部分常量和全局/静态数据主要来自 Mach-O。启动时，内核与 dyld 将 Mach-O 的 Segment 和 Section 映射为 VM Region。
- 堆是运行期间由分配器管理的动态分配区域，可能由多个 Region 组成，不是一条与栈相向增长的连续线。
- 每个线程都有自己的栈，用来支持函数调用和临时状态。局部变量在未优化构建中通常能在栈帧中观察到，优化后也可能进入寄存器或被消除。
- Framework、dyld shared cache、内存映射文件和 Guard Page 等真实映射并不适合硬塞进“五大分区”。内核统一用 VM Region 描述连续且属性相近的虚拟地址范围。

Mach-O 中，Segment 是装载和权限管理的大单位，Section 是对具体内容的细分。例如机器指令通常位于 `__TEXT,__text`，已初始化可写全局变量通常位于 `__DATA,__data`，零初始化全局或静态变量通常位于 `__bss` 或 `__common`。

#### VM Region 的来源和访问权限怎样理解？

VM Region 是内核和调试工具描述进程虚拟地址空间的实际单位之一：一段连续的虚拟地址范围，拥有相近的保护权限、映射来源和其他属性。

常见来源包括：

- 主程序、Framework、dyld shared cache 或 `mmap` 文件形成的文件映射；
- 分配器管理的匿名内存；
- 每个线程的栈与 Stack Guard；
- `__PAGEZERO` 等保护或保留区域。

常见权限为：

- `r--`：可读，常见于只读数据；
- `rw-`：可读写，常见于全局可写数据、堆和线程栈；
- `r-x`：可读可执行，常见于机器指令；
- `---`：不可读写执行，常见于 `__PAGEZERO` 或 Stack Guard。

访问权限与页面状态不能混为一谈：一个 Region 可以显示 `rw-`，页面内容在尚未修改时仍可能是 clean；写入 Copy-on-Write 映射后才形成 private dirty page。

Region 能告诉我们地址范围、权限和大致来源，但不能直接告诉我们其中有几个 Objective-C 对象，也不能用 Region 大小推导当前驻留物理内存或 Memory Footprint。

#### 操作系统的“分段”、分页和 Mach-O Segment 是一回事吗？

不是。

- 操作系统教材中的 Segmentation 是一种按逻辑段组织地址空间并参与地址转换的经典内存管理模型。
- 分页把虚拟内存和物理内存划分为固定大小的页与页框，由页表记录映射及权限。现代 arm64 iOS 的地址管理重点是分页、页表和 Mach VM。
- Mach-O 的 Segment 是可执行文件和装载映射的组织单位，例如 `__TEXT`、`__DATA_CONST`、`__DATA`，不是 CPU 分段机制。
- 堆和线程栈是进程运行时使用的虚拟内存区域，也不是“编译器创建的 CPU 分段”。

较新的 64 位 iOS 设备通常向用户空间暴露 16 KiB 页面。

#### Mach-O 中的 `__PAGEZERO` 和 `__LINKEDIT` 有什么作用？

`__PAGEZERO` 在 64 位 Mach-O 中保留低地址范围，但不映射成可读、可写或可执行内存。这样空指针附近的错误访问更容易立即失败，而不是落入一段看似有效的业务数据。

`__LINKEDIT` 保存符号表、字符串表、重定位和其他链接编辑信息，供 dyld 装载、符号解析以及调试工具使用。它不属于“五大分区”中的业务代码或业务数据，但属于进程映像和链接体系的一部分。

#### ASLR 为什么让同一函数每次运行的地址不同？它与符号化有什么关系？

Mach-O 记录链接地址、大小和权限等装载信息。系统启动进程时会引入随机的 ASLR Slide：
```text
运行时地址 = Mach-O 链接地址 + ASLR Slide
```
同一映像中的函数、全局数据和字面量会跟随映像整体移动，相对布局与权限通常保持一致。它们没有因为绝对地址变化而进入别的 Section。栈和堆则由线程、分配器和当次运行状态决定，不能使用主程序 Mach-O 的 slide 进行同样推导。

符号化会先根据运行时地址确定它属于哪个镜像，再减去该镜像自己的 slide，得到链接地址，最后用 dSYM 查询函数名和源码行。使用错误镜像的 slide，或直接比较不同进程、不同次运行的绝对地址，都没有意义。

#### iOS 的栈和堆会固定地相向增长吗？什么是栈溢出？

arm64/iOS 的线程栈通常向低地址增长：函数需要更多栈空间时，栈指针 `SP` 向较小地址移动，返回时再恢复。但不能顺势推导“堆一定从低地址向高地址，与栈相向增长”。现代分配器管理多个 VM Region，堆不是一条方向固定、连续增长的线。

每个线程都有自己的栈 Region。一次函数调用可能建立栈帧，保存部分局部变量、溢出到栈上的参数、返回地址和需要恢复的寄存器；真实位置会受调用约定和编译优化影响。

递归过深或函数长期占用大量栈空间时，栈帧不断累积，最终越过可用栈区域或触碰 Stack Guard，就会产生栈溢出并崩溃。多个线程共享代码、全局数据和堆，但不共享同一个线程栈。

### 内存压力、Jetsam 与 OOM

#### Memory Warning、Jetsam 和 OOM 是什么关系？

Memory Warning 是 UIKit 层的建议性通知。它表示系统内存压力较大，App 仍有机会释放可重建且当前不需要的资源，但系统不保证在终止进程前一定发送警告。

Jetsam 是内核层的强制终止机制。系统可能因为某个进程超过自身限制，或整体压力需要快速回收资源而直接终止它。Jetsam Event Report 与普通崩溃报告不同，分析重点是终止原因、内存状态和进程状态，不一定存在一条指向业务代码的崩溃调用栈。

iOS 工程中常说的 OOM，通常指高内存使用导致的系统终止。

泄漏和无上限缓存会造成持续增长；大图解码、多份大数据同时存活、并发任务过多或新旧资源短暂共存，则会制造瞬时峰值。即使没有泄漏，也可能因为峰值导致 OOM。

### 存储期、指针与对象语义

#### `id obj = [NSObject new]` 后，局部变量、指针值、对象本体分别在哪里？

`obj` 是局部指针变量。它通常位于当前线程的栈帧；优化后可能只存在于寄存器，甚至被消除。`obj` 中保存的是对象地址；`[NSObject new]` 创建的普通对象本体通常位于分配器管理的堆区域。`&obj` 是指针变量自己的地址，`obj` 是变量里保存的对象地址，二者不是同一个地址。

字符串字面量和 Tagged Pointer 是需要另外说明的例外：字符串字面量通常来自只读 Mach-O 映射；Tagged Pointer 直接把类型和值编码在指针中，没有它所指向的普通堆对象本体。

#### 文件作用域 `static` 和函数局部 `static` 有什么区别？

`static` 在不同位置控制的事情不同。

文件作用域变量本来就具有静态存储期，程序运行期间始终存在；添加 `static` 主要把符号从 external linkage 改成 internal linkage，使其他编译单元不能通过该符号引用它。它不会因此进入一个单独的“静态区”。

```objc
static int fileCount = 0; // 静态存储期 + 文件内链接可见
```

函数局部 `static` 的名字仍然只在函数作用域内可见，但它对应的对象具有静态存储期，整个进程生命周期中通常只有一份，并由静态可写数据映射承载，而不是每次调用都在栈上创建：

```objc
void test(void) {
    static int callCount = 0;
    int localCount = 0;
    callCount++;
    localCount++;
}
```

多次调用时，`callCount` 会保留前一次的值；`localCount` 每次重新初始化。两次调用中局部变量地址恰好相同，只能说明栈帧位置被复用，不能说明普通局部变量具有静态存储期。

#### Objective-C 方法传递对象时，传的是对象还是指针？

传入的是对象指针值的一份副本，不会复制整个对象：
```objc
static void ReplaceObject(NSObject *object) {
    object = [NSObject new];
}
```
函数内部的 `object` 是新的局部指针变量。给它重新赋值只改变这个副本的指向，不会修改调用方的指针变量。

但如果双方的指针都指向同一个可变对象，方法向这个对象发送修改消息，调用方能够观察到对象状态变化：

```text
object = anotherObject
→ 改变局部指针的指向

[object mutate]
→ 根据指针找到双方共享的对象
→ 修改对象内部状态
```

#### 为什么 `NSError **` 能修改调用方的指针？

`NSError *error` 保存的是错误对象地址；`&error` 是局部指针变量 `error` 自己的地址，类型为 `NSError **`。

```objc
NSError *error = nil;
BOOL success = [manager loadData:&error];
```

普通 `NSError *` 参数只能获得对象地址的副本；`NSError **` 参数拿到了调用方指针变量的存储位置，因此被调用方法可以把新的错误对象地址写回 `error`。ARC 下常见的 Cocoa 错误输出参数还会涉及 `__autoreleasing` 所有权推断。

#### `self.name`、`_name` 和局部变量 `name` 是一回事吗？

不是。

- 局部 `name` 是当前函数中的指针变量，未优化时通常可在栈帧中观察到。
- `_name` 是对象内部的实例变量，存储跟随对象本体；如果类型是 `NSString *`，它保存的通常仍是另一个对象的地址，并没有把整个字符串嵌入当前对象。
- `self.name` 是属性访问表达式。读取通常调用 `name`，赋值通常调用 `setName:`。

```objc
self.name = name; // 调用 setter
_name = name;     // 直接修改 ivar，绕过 setter
```

属性不是新的内存分区。自动合成属性时，真正提供存储的是后备实例变量。

#### `strong` 和 `weak` 决定指针变量在栈还是堆吗？

不决定。`strong` 和 `weak` 描述所有权关系：strong 会维持对象生命周期，weak 不会延长生命周期，并在对象销毁后置为 `nil`。

栈、寄存器和对象内部 ivar 回答“这个指针变量存在哪里”；strong、weak 回答“这条引用是否拥有对象”。局部 strong 指针仍可能位于栈或寄存器，对象内部的 weak ivar 则跟随对象本体。

因此“strong 在堆上，weak 在栈上”是错误说法。

#### 执行 `object = nil`，对象会马上销毁吗？

不一定。把一个 strong 指针赋值为 `nil`，只会解除这一条强引用：

```objc
NSObject *first = [NSObject new];
NSObject *second = first;
first = nil;
```

`second` 仍然强引用原对象，所以对象继续存活。赋 `nil` 改变的是 `first` 保存的指针值，不是直接擦除对象内存。只有最后一条强引用消失后，对象才具备结束生命周期的条件。

#### `==`、`isEqual:` 和 `hash` 分别是什么关系？

对于对象指针，`==` 比较的是两个指针值，也就是判断是否指向同一个对象；`isEqual:` 询问对象定义的逻辑相等关系，两个不同对象可以表示相同的值。

```objc
BOOL sameObject = (first == second);
BOOL sameValue = [first isEqual:second];
```

自定义类如果重写 `isEqual:`，并准备把实例用于 `NSSet`、`NSDictionary` 等哈希集合，还必须维持：

```text
[a isEqual:b] == YES
        ↓
a.hash == b.hash
```

反过来，hash 相同不代表对象一定相等，因为哈希冲突是允许的。

## 对象模型与类结构

### 对象的实例布局与分配大小

#### 普通对象为什么可以概括成“isa + ivar”？实例中是否保存方法？

普通实例对象开头是 isa，后面依次是父类与本类的实例变量，并按各自对齐规则排布。实例中不保存方法；方法元数据位于类或元类的数据结构中。

`objc_object` 源码只声明公共对象头，没有列出每个具体类的 ivar。编译器会为 ivar 生成偏移元数据，Runtime 分配对象时按类的实例大小在 isa 后预留空间。访问 `object->_age` 的底层思想是：

```text
(char *)object + ivar.offset
```

因此它不是在运行时把一个 C 结构体字段“追加”进 `objc_object` 的源码定义，而是按照类元数据描述的偏移访问对象尾部的实例存储。继承来的 ivar 也属于对象布局的一部分。

#### `sizeof(object)` 能得到 Objective-C 对象的大小吗？

不能。在 64 位环境中，`sizeof(object)` 通常是 8，因为它测量的是对象指针类型的宽度，不是对象本体大小。

```text
sizeof(object)
→ 指针本身占多少字节

class_getInstanceSize([object class])
→ 该类实例布局至少需要多少字节

malloc_size((__bridge const void *)object)
→ 分配器实际为普通堆对象提供了多大的块
```

后两个数也不一定相同，分配器可能按照大小等级向上取整。`malloc_size` 不能用于 Tagged Pointer，因为它没有对应的普通堆分配地址。

#### `instanceSize`、`class_getInstanceSize` 和 `malloc_size` 为什么可能不同？

这三个数处在不同层次：

1. `class_ro_t.instanceSize` 表示编译器计算出的 isa 加全部 ivar 的布局需求。
2. `class_getInstanceSize` 返回按机器字等规则对齐后的实例布局需求。
3. 真正创建实例时，Runtime 还会应用对象分配的最小值；分配器再按自己的 size class 向上取整，`malloc_size` 反映普通堆块的实际可用大小。

典型 64 位结果是：只有 isa 的 `NSObject` 理论布局需求为 8 字节，`class_getInstanceSize` 也可能是 8，但真正分配至少为 16，`malloc_size` 因此得到 16。若“isa + ivar”需要 20 字节，布局对齐可能为 24，而 malloc 桶最终可能给 32。

`sizeof(obj)` 仍只是在测指针宽度；`malloc_size` 也不能用于 Tagged Pointer。

### Runtime 基础与对象头

#### Objective-C Runtime 是什么？“动态”具体动态在哪里？

Runtime 是支撑 Objective-C 对象模型、消息发送和动态能力的一套运行时系统，主体由 C/C++ 与少量汇编实现。Objective-C 方法调用不是在编译期完全绑定成一次固定的 C 函数调用，而是把接收者和 selector 交给类似 `objc_msgSend` 的消息发送流程，在运行期根据对象的真实类型查找并执行对应的 `IMP`。

Runtime 还负责注册类、连接类与元类、整合 Category，以及提供动态查询和修改类、方法、属性、协议的 API。消息转发、关联对象、Method Swizzling、Category 和 KVO 等能力，都建立在这套动态对象模型之上。

“动态”不等于所有事情都拖到运行时才做。编译器仍会生成类的初始元数据和消息发送代码；Runtime 负责把需要结合真实类型、加载顺序和运行状态才能决定的部分在运行期完成。

#### `id`、`Class` 和 `SEL` 在底层分别是什么？

公开头文件中的核心类型可以简化为：

```objc
typedef struct objc_object   *id;
typedef struct objc_class    *Class;
typedef struct objc_selector *SEL;
```

- `id` 是指向 Objective-C 对象的指针类型，不在编译期限定具体类。
- `Class` 是指向 `objc_class` 的指针。普通类和元类都用这个类型表示。
- `SEL` 是方法名字在 Runtime 中的唯一标识，用来参与 `SEL → IMP` 查找；它不是方法实现本身。

#### 新版 `objc_object` 为什么使用 `isa_storage`，对象头是否因此改变了？

旧版内部实现常直接写成 `isa_t isa`；较新的 objc4 内部实现使用：

```cpp
char isa_storage[sizeof(isa_t)];
isa_t &isa() {
    return *reinterpret_cast<isa_t *>(isa_storage);
}
```

两种写法描述的仍是对象开头同一个机器字。假设 `sizeof(isa_t) == 8`，它们都只占 8 字节；`reinterpret_cast` 只是把这 8 字节临时解释成 `isa_t`，不会复制或再创建一个 isa，也不会改变后续 ivar 的位置。

新版主要把存储细节隐藏起来，要求 Runtime 通过受控访问器统一处理 non-pointer isa、原子操作和 arm64e 的指针认证。还要区分公开 `objc.h` 中便于声明类型的兼容表示与 objc4 私有头文件中的真实内部实现，总体来说只是换了个包装，无本质性区别。

#### `isa()`、`ISA()`、`rawISA()` 和 `getIsa()` 有什么区别？

- `isa()`：把对象头的原始字节解释成 `isa_t`，返回 `isa_t` 引用，是更底层的内部访问器。
- `ISA(authenticated)`：从普通对象的 isa 信息中解析出 `Class`，可选择是否执行 PAC 认证；它假定接收者不是 Tagged Pointer。
- `rawISA()`：只适用于 raw isa 等满足其前提的情况，不能拿来通用 non-pointer isa 和 Tagged Pointer。
- `getIsa()`：允许接收者是 Tagged Pointer。普通对象走 `ISA()`；Tagged Pointer 则从 tag 查 Runtime 的类表。

#### `isa_t` 为什么被设计成 union？`bits`、`cls` 和位域是什么关系？

`isa_t` 是一个与指针同宽的 union。union 的成员共享同一块内存，因此：

- `bits` 把整个机器字当作无符号整数，便于掩码和位运算；
- `cls` 把同一机器字当作 `Class` 指针理解；
- 匿名位域把同一机器字拆成 `nonpointer`、类信息、引用计数和状态标志等字段。

这是同一组位的三种观察方式。arm64e 上 `cls` 被放在 private 区域，是因为类指针可能带 PAC 签名，调用方不能绕过 `getClass`、`setClass` 直接当作普通地址使用。

### non-pointer isa、PAC 与 Tagged Pointer

#### raw isa 和 non-pointer isa 有什么区别？（疑）

raw isa 可以近似理解为“对象头这个机器字主要就是一根普通 Class 指针”；non-pointer isa 则利用指针对齐和地址没有占满全部位宽的空间，把类信息与多个状态位压进同一个机器字。

在支持 non-pointer isa 的普通对象中，常见信息包括：

- 对象所属类的信息；
- 是否有关联对象；
- 是否曾被 weak 引用；
- 一部分内联引用计数 `extra_rc`；
- 引用计数是否已经溢出到 SideTable。

因此不能把任意 isa 值直接强转为 Class。必须按照当前平台的布局、掩码和 PAC 规则解析。有些类或特殊对象还会因为 Runtime 条件而要求使用 raw isa，不能假设所有对象都一定是 non-pointer isa。

#### non-pointer isa 中几个常见字段分别表示什么？

- `nonpointer`：是否采用“类信息 + 标志位”的压缩 isa；为 0 时通常按 raw isa 处理。
- `has_assoc`：对象是否设置过关联对象。它通常是单向状态，设置过后不一定因为全部移除就恢复为 0。
- `weakly_referenced`：对象是否进入过 weak 引用管理流程。
- `has_sidetable_rc`：内联区域容纳不下全部引用计数，是否还需要查询 SideTable。
- `extra_rc`：保存在 isa 中的额外引用计数，不应简单理解为对外可见的完整 `retainCount`。
- `shiftcls` 或 `shiftcls_and_sig`：压缩后的类信息；arm64e 版本还合并了 PAC 签名。

#### 为什么旧源码中的类字段叫 `shiftcls`，常看到 Class 指针右移 3 位？

Class 对象通常按 8 字节对齐，合法地址的最低 3 位恒为 0。存储时可以把 Class 指针右移 3 位，省掉不携带信息的低位；读取时再左移还原。这就是 `shiftcls` 名称和老源码中 `cls >> 3` 思路的来源。

这是利用对齐产生的低位空洞。现代 arm64e 使用 `shiftcls_and_sig`，其中还混入 PAC 签名，不能再机械套用“只右移、再左移”的旧解释。

#### arm64e 的 Pointer Authentication 如何保护 isa？

PAC 会根据指针值、硬件保护的密钥和修饰子计算签名，并把签名存进指针未用于寻址的高位。Runtime 给 isa 使用固定用途的 discriminator，同时把对象自己的地址混入修饰子，所以 isa 的签名同时绑定了“这是 isa”以及“它属于这个对象”。

结果是：攻击者即使把 A 对象上一段看似合法的 isa 位模式复制到 B 对象头，认证也可能因为对象地址不同而失败。Runtime 对 `superclass`、部分 `IMP`、缓存 bucket 和类数据指针也会采用类似思路，但使用不同的用途修饰子，避免不同类型的已签名指针互相替代。

#### `isa_t::getClass(authenticated)` 怎样从 isa 中取出 Class？

在非 arm64e 平台，核心思路是读取 `bits`，再用当前架构的 `ISA_MASK` 去掉标志位和引用计数位，留下类地址。

在 arm64e 上有两条路径：

- `authenticated == true`：保留类信息和签名，使用与该 isa 地址绑定的 discriminator 做 PAC 认证，成功后得到可用的 Class；
- `authenticated == false`：使用运行期掩码直接去掉签名和状态位，取得地址，速度更快但不验证完整性。

索引式 isa 则可能保存类表索引而不是直接保存类指针。由此可见，“读 isa 等于做一次指针强转”只适用于过度简化的旧模型。

#### Tagged Pointer 为什么能节省一次堆分配？

普通小对象通常需要一个指针变量，再在堆上分配对象本体；Tagged Pointer 则把类型标记和小数据直接编码进指针值，因此不需要普通堆对象本体，也省去了这次分配、引用计数维护和释放成本。

它能够正常接收消息，是因为 Runtime 在解引用接收者之前先判断它是不是 Tagged Pointer。若是，就从指针位模式中取得 tag，用 tag 直接索引 Runtime 类表，得到 Class 后再进入正常的方法缓存和查找流程。这个类表更接近直接索引数组，不是需要计算 hash、处理冲突的散列表。

它没有普通对象本体和 isa，因此：

- `retain`、`release`、`autorelease` 不走普通对象的引用计数和自动释放池路径；
- weak 注册会跳过 weak table，因为不存在普通对象销毁后清除弱引用的过程；
- 普通 ivar 依赖“对象地址 + ivar offset”，Tagged Pointer 没有这块存储，所以不能承载普通实例变量；
- 关联对象存储在对象本体之外，可以把 Tagged Pointer 的位值当作关联身份，因此它仍然可以使用关联对象。

没有一次普通堆分配不代表完全没有内存成本。保存它的局部变量、数组或字典中的元素槽位，以及 Runtime 类表本身仍然需要空间。准确说法是：相较于为同一个小值创建普通对象，它省去了独立对象本体及其引用计数管理。

#### Tagged Pointer 中的 Payload、Tag 和 Extended Tag 分别是什么？

- Payload：真正承载的小值内容，例如数字、日期信息或特定字符串编码；具体解释由相应 Foundation 类型决定。
- Tag：很小的类型编号。它不是 Class 指针，Runtime 用它索引 tagged class 表以取得真正的 Class。
- Extended Tag：基础 Tag 不够用时的二级类型编号。它增加可表示的类型数量，但会占用更多位，因此留给 Payload 的位数更少。

值超出某种 tagged 格式的容量时，会退回普通堆对象，而不是截断。不同平台和系统版本的标志位、Tag 位置与具体类型编号都可能变化；较新的系统还会用全局 obfuscator 对位模式异或混淆，进一步防止业务代码硬编码私有布局。

### 类对象、类数据与 realize

#### 为什么说类本身也是对象？`objc_class` 的四个核心部分是什么？

`objc_class` 继承自 `objc_object`，所以类对象开头同样有 isa。类对象的 isa 指向元类。随后可以概括为四个核心部分：

1. `isa`：指向对应元类；
2. `superclass`：指向父类，形成普通继承链；
3. `cache`：缓存热点 `SEL → IMP`；
4. `bits`：类数据入口，指向 `class_ro_t` 或 realize 后的 `class_rw_t`，再按需连接 `class_rw_ext_t`。

在 arm64e 上，`superclass` 这样的关键指针也可能带 PAC，Runtime 会通过访问器签名或认证，不能依赖私有字段直接读取。

#### `isa_t.bits` 和 `class_data_bits_t bits` 是同一个东西吗？

| 对比 | `isa_t.bits` | `class_data_bits_t.bits` |
| --- | --- | --- |
| 所在位置 | 每个普通对象的对象头 | `objc_class` 的类数据字段 |
| 主要指针载荷 | 对象所属 Class | `class_ro_t *` 或 `class_rw_t *` |
| 附加信息 | 引用计数、weak、关联对象等 isa 状态 | Swift、默认 RR、是否已经指向 rw 等类状态 |
| 回答的问题 | 这个对象属于哪个类 | 这个类的数据在哪里 |

#### `objc_class.bits → class_ro_t / class_rw_t / class_rw_ext_t` 的关系是什么？

类尚未 realize 时，`bits` 直接指向编译产物中的 `class_ro_t`。类第一次真正被 Runtime 使用后，Runtime 分配 `class_rw_t`，让 `bits` 改为指向 `rw`；`rw` 再保留对原始 `ro` 的引用。

大多数类只需要 `ro + rw`。只有合并 Category、动态增改方法/属性/协议或保存少见扩展信息时，才懒分配 `class_rw_ext_t`：

```text
未 realize：bits → ro

已 realize：bits → rw → ro

需要扩展： bits → rw → rw_ext
                           ├─ ro
                           ├─ methods
                           ├─ properties
                           └─ protocols
```

因此 `ro`、`rw`、`rw_ext` 不是三个互相替代且内容完全相同的版本，而是编译期只读数据、运行期状态外壳和按需可变扩展三种职责。

#### `class_ro_t` 中主要保存什么？为什么叫 ro？

`class_ro_t` 保存编译期已经确定的类元数据，例如：

- 类标志、类名；
- `instanceStart`、`instanceSize`；
- 原始实例方法列表、协议列表和属性列表；
- ivar 列表及每个 ivar 的偏移；
- strong/weak ivar 布局信息；
- 元类场景下复用的 `nonMetaclass` 等信息。

它通常位于镜像的只读、文件支持页面，内容可从 Mach-O 或 dyld shared cache 重新取得，因此适合保持为 clean memory。`ro` 指的是这份编译期基础数据不可直接在原位置随意修改，不代表整个类在运行时都不可变。

#### `class_rw_t` 和 `class_rw_ext_t` 分别保存什么？

`class_rw_t` 是类被 realize 后创建的可写外壳，主要保存运行期 flags、状态、子类链的 `firstSubclass` / `nextSiblingClass`，并通过 `ro_or_rw_ext` 连接 `ro` 或 `rw_ext`。

`class_rw_ext_t` 保存不一定每个类都需要的扩展内容，例如可变 methods、properties、protocols、Swift demangled name 和 version。它还保留对 `ro` 的引用，使基础数据不会丢失。

拆分的关键是懒分配：类只要被使用就可能需要一个小的 `rw`，但只有确实要合并或修改扩展数据时才分配更大的 `rw_ext`。这避免所有类都为低频能力支付常驻 dirty memory 成本。

#### 为什么 objc4 要把类数据拆成 clean 的 ro 和 dirty 的 rw/rw_ext？

文件支持且未修改的 clean page 在内存压力下可以丢弃，之后从文件重新载入；运行期写过的 dirty page 必须保留其私有内容，或由系统压缩保存，成本更高。iOS 又不像 macOS 那样依赖传统磁盘交换，因此减少 dirty memory 尤其重要。

类名、初始实例大小和编译期方法列表不会频繁变化，适合留在 `ro`；运行期 flags、继承遍历状态、Category 合并和动态方法修改必须可写，放进 `rw/rw_ext`。WWDC 2020 的优化进一步把少数类才用到的可变数组拆进懒分配 `rw_ext`，让大部分类保持更小的运行期写时数据。

这与进程内存章节的原则一致：减少的不只是结构体字节数，更重要的是避免只改一个小字段就把整页文件映射变成进程私有 dirty page。

#### 类的 realize 过程做了什么？

类最初从镜像加载时，`bits` 可能仍指向 `ro`。第一次真正使用类时，`realizeClassWithoutSwift` 大致会：

1. 通过 `safe_ro()` 取得只读数据；此时不能假设 `data()` 已经能返回 rw。
2. 分配并初始化 `class_rw_t`，把 `ro` 接入其中。
3. 设置 realized/realizing 等状态，并让 `bits` 从“指 ro”翻转为“指 rw”。
4. 递归 realize 父类和元类，回写 `superclass` 与类对象的 isa。
5. 通过 methodize 等流程安装基础方法、属性、协议，并合并已加载的 Category。

realize 不是“创建类名”这么简单，而是把编译期静态描述接成 Runtime 可使用、可扩展的完整类结构。它也不同于 `+initialize`：前者是 Runtime 构造类内部状态，后者是 Objective-C 类收到首次消息前的初始化回调语义。

#### 为什么读取未 realize 类的只读数据要用 `safe_ro()`，不能直接调用 `data()`？

现代实现中，`data()` 的语义是取得 `class_rw_t *`，内部会断言 `bits` 已经标记为 rw 指针。未 realize 时 `bits` 仍直接保存 `class_ro_t *`，所以把它当 rw 读取会类型错误或触发断言。

`safe_ro()` 会先检查 `bits` 当前处于 ro 还是 rw 状态：若仍是 ro，按 ro 指针解析；若已经是 rw，则通过 `rw->ro()` 找回只读数据。它还要兼顾并发 realize 和 arm64e 的认证要求。

### 消息查找、方法缓存与 IMP

#### `cache_t` 在一次消息发送中起什么作用？

对普通对象发送消息时，Runtime 先通过 isa 找到类，然后优先查询该类的缓存：

```text
receiver → Class → cache_t
                    ├─ 命中：直接取得 IMP
                    └─ 未命中：查本类方法列表
                                  ↓
                              沿 superclass 查找
                                  ↓
                         找到后回填接收者类的缓存
```

如果继承链都找不到，才进入动态方法解析和消息转发等流程。缓存针对高频重复消息减少方法列表扫描和父类遍历，它保存的是 selector 到实现的映射，不是把整个方法对象复制到实例中。

#### `cache_t`、`bucket_t`、mask 和 occupied 分别表示什么？

`cache_t` 的核心存储可以理解为一组 buckets。每个 `bucket_t` 是一个 `SEL → IMP` 槽位；mask 用来快速把 selector 映射到容量范围内的初始下标；occupied 表示已经使用的槽位数量，便于判断负载和扩容时机。发生冲突时按 Runtime 的探测规则继续查找其他槽位。

现代 `cache_t` 会根据平台把 buckets 指针、mask、flags 或预优化缓存信息压缩到少量机器字中。`_flags` 还可承载元类标记、C++ 构造/析构标记、默认方法标志和快速实例大小等高频信息。arm64e 下 bucket 中的 IMP 也可能被编码或签名，读取时要按对应规则恢复。

#### 什么是预优化方法缓存？为什么类刚 realize 时不能立即使用它？

普通 `cache_t` 要等某个 selector 第一次慢速查找成功后才缓存 `SEL → IMP`。对于 dyld shared cache 中符合条件的系统类，shared cache builder 可以提前生成 `preopt_cache_t`，使进程无需完全从空缓存开始。

但类首次使用还涉及 `+initialize` 的同步与时序。刚 realize 时必须保证消息能够进入需要的慢路径，不能让预优化命中绕过初始化检查。因此 Runtime 会先把预优化缓存以“伪装”状态保存；类初始化完成后再验证并正式启用，若条件不满足则丢弃并回到普通空缓存。

预优化缓存主要是系统共享缓存层面的启动和内存优化，不应理解为所有 App 类都在编译期拥有一份永远正确的消息缓存。

#### `IMP` 是什么？为什么直接调用 IMP 必须精确转换函数类型？

`IMP` 是 Objective-C 方法最终实现的函数地址。selector 负责标识“方法叫什么”，缓存和方法列表负责建立 `SEL → IMP` 的映射。可以通过 `methodForSelector:` 或 `instanceMethodForSelector:` 取得某个调用路径最终使用的实现。

Objective-C 方法的底层调用还包含隐式参数 `self` 和 `_cmd`。若绕过 `objc_msgSend` 直接调用 IMP，必须把它转换成与返回值、显式参数、结构体传参和调用约定完全匹配的函数指针类型。类型不匹配属于未定义行为，可能造成寄存器解释错误、栈损坏或返回值读取错误。

#### 相对方法列表为什么能减少内存占用和 Dirty Memory？

传统方法条目包含 name/selector、type encoding 和 IMP 三根 64 位指针，一项通常需要 24 字节。相对方法列表可以用三个 32 位相对偏移表示，同样信息约为 12 字节，体积减半。

相对偏移以条目自身地址为基准计算，镜像加载到不同 ASLR 地址时通常无需把每根绝对指针重新 rebase。这样方法列表更容易继续停留在 clean 的文件映射或 dyld shared cache 中，也便于多进程共享。代价是 32 位相对范围有限，目标通常需要位于约 ±2 GiB 内，极少数不满足条件的场景要回退到其他表示。

Method Swizzling 也不应直接改坏原始只读列表。现代实现可以通过额外映射或可写结构记录替换，避免只交换一个实现就把承载大量方法的整个文件页弄脏。

### 元类与继承链

#### 元类为什么没有独立的结构体？类方法到底存在哪里？

元类和普通类都用 `objc_class` 表示，不需要另一套结构体。Runtime 通过 `RO_META`、`RW_META` 或 cache 中的快速标志判断某个 Class 是否为元类。

类方法本质上存放在元类的方法列表中，并作为元类的“实例方法”参与同一套查找。例如 `class_getClassMethod(cls, sel)` 的底层思路，就是先取得 `cls` 的元类，再在元类上查询同名实例方法。

因此：

```text
实例对象 --isa--> 普通类 --保存实例方法
类对象   --isa--> 元类   --保存类方法
```

类对象之于元类，正如实例对象之于普通类。这样消息发送不需要为 `+` 方法另造一套完全不同的机制。

#### 类尚未 realize 时，Runtime 怎样判断它是不是元类？

realize 后可以从 `class_rw_t` 的 `RW_META` 或 cache 的快速 META 标志判断；尚未 realize 时还没有 rw，Runtime 则从 `class_ro_t` 的 `RO_META` 判断。

现代实现特意让 `class_ro_t` 和 `class_rw_t` 的 flags 位于可兼容读取的位置，并让 `RO_META` 与 `RW_META` 使用一致的标志值。这样 `bits.flags()` 可以在不先强制 realize 类的情况下判断元类状态。它再次说明 ro/rw 的布局虽属私有实现，却经过了热路径和状态转换方面的精心设计。

#### 实例、类对象、元类之间的 `isa` 与 `superclass` 链

实例的 `isa` 指向所属类对象，类对象的 `isa` 指向对应元类；非根元类的 `isa` 最终指向根元类，根元类的 `isa` 指向自己。

普通类的 `superclass` 按“子类 → 父类 → `NSObject` → `nil`”向上走。元类的 `superclass` 按“子类元类 → 父类元类 → `NSObject` 根元类 → `NSObject` 类 → `nil`”向上走，使类方法也能继承。

可以把 `object_getClass` 理解成沿 `isa` 关系走一步，把 `class_getSuperclass` 理解成沿 `superclass` 关系走一步，但业务代码不应自行读取私有的 isa 位布局。

#### 实例、普通类、元类的完整 isa 与 superclass 链怎样闭合？

以 `Dog : Animal : NSObject` 为例：

- isa：`dog 实例 → Dog 类 → Dog 元类 → NSObject 根元类`；根元类的 isa 指向自己形成闭环。
- 普通 superclass：`Dog 类 → Animal 类 → NSObject 类 → nil`。
- 元类 superclass：`Dog 元类 → Animal 元类 → NSObject 根元类 → NSObject 类 → nil`。

根元类的 `superclass` 拐回 `NSObject` 类，使类方法查找沿元类继承链走到根部后，仍能获得根类定义的公共行为；根元类的 isa 指向自己，则为 isa 链提供稳定终点。

类的 isa、superclass 连接和父类/元类的递归 realize 是同一套 Runtime 构建过程的一部分。业务代码应使用 `object_getClass`、`class_getSuperclass` 等 API 验证关系，不要按私有结构偏移直接解引用。

### 类型判断、Runtime 查询与 API 边界

#### `isKindOfClass:` 为什么要区分接收者是实例还是类对象？

实例调用 `-isKindOfClass:` 时，从实例所属的普通类开始沿 `superclass` 查找；类对象调用 `+isKindOfClass:` 时，先通过 `isa` 到元类，再沿元类的 `superclass` 链查找。因此，同一个目标 Class 在实例接收者和类对象接收者上可能得到不同结果。

`isMemberOfClass:` 只比较查找起点，不继续走父类链；`isKindOfClass:` 会继续沿 `superclass` 查找。做判断题之前，必须先确定接收者是实例对象还是类对象。

#### `isSubclassOfClass:` 与对类对象调用 `isKindOfClass:` 有什么区别？

`[Dog isSubclassOfClass:Animal.class]` 从 `Dog` 这个普通类开始，沿普通类的 superclass 链查找，适合判断类继承关系。它把同一个类也算作 YES，因此如果要判断严格子类，还要额外排除相等。

`[Dog isKindOfClass:...]` 的接收者是类对象，它从 `Dog` 的元类开始沿元类链查找，回答的是类对象自身在元类关系中的类型问题，并不等价于“Dog 是否继承自目标类”。

```objc
[Dog isSubclassOfClass:Dog.class]; // YES
[Dog isKindOfClass:Dog.class];     // 通常 NO
```

判断对象归属使用 `isMemberOfClass:` / `isKindOfClass:`；判断两个类的继承关系优先使用 `isSubclassOfClass:`。

#### `isKindOfClass:` 是否每次都一定通过 `objc_msgSend` 执行？

不一定。当前 Runtime 可以使用 `objc_opt_isKindOfClass` 一类快路径：如果接收者不为 `nil`，并且它的类没有重写 `isKindOfClass:` 等 NSObject 核心行为，Runtime 可以直接用 C 循环从真实 Class 开始沿 `superclass` 比较，省去一次完整消息发送。

如果类存在自定义核心行为，快路径就必须放弃优化，回到 `objc_msgSend`，保证重写的方法仍有机会决定结果。因此，稳定语义仍是“沿继承关系判断”，是否绕过消息发送属于实现优化，业务代码不能依赖。

#### `isAncestorOfObject:` 与 `isSubclassOfClass:` 是什么关系？业务代码能否使用？

objc4 源码中还能看到 `+isAncestorOfObject:`：它从某个对象的真实类开始沿 `superclass` 向上查找，询问“当前类是不是这个对象所属类的祖先”。可以把它理解成从对象一侧观察继承关系，与从类一侧调用 `isSubclassOfClass:` 相互对照。

但它不属于当前公开 `NSObject` API，业务代码不应私自声明并调用。实际需求应使用公开的 `isKindOfClass:`、`isMemberOfClass:` 或 `isSubclassOfClass:` 表达。

#### `[obj class]` 和 `object_getClass(obj)` 是否相同？

对普通 NSObject 实例，它们通常得到相同 Class，但语义不同：

- `[obj class]` 是 Objective-C 消息发送，类可以重写 `-class`，向外报告一个更稳定或被隐藏的类型；
- `object_getClass(obj)` 是 Runtime C API，沿对象当前的 isa 关系取得真实运行时类。

KVO 动态子类是经典例子：对象的实际 isa 可能被改到自动生成的子类，而 `-class` 可以继续对外返回原始类。对一个类对象调用 `object_getClass(SomeClass.class)`，得到的是其元类；`[SomeClass class]` 通常仍返回普通类对象自身。

#### `object_getClass`、`class_getSuperclass` 和 `class_isMetaClass` 分别沿哪条关系工作？

- `object_getClass(obj)`：沿 obj 的 isa 关系走一步；实例得到普通类，普通类得到元类。
- `class_getSuperclass(cls)`：沿传入 Class 的 superclass 走一步；传普通类就走普通继承链，传元类就走元类继承链。
- `class_isMetaClass(cls)`：判断当前 Class 节点是不是元类，不负责继续走链。

如果只有名字，可以使用 `NSClassFromString(@"Dog")` 或 `objc_getClass("Dog")` 取得普通类；`objc_getMetaClass("Dog")` 直接取得对应元类。前者使用 `NSString`，后两者使用 C 字符串。

#### `respondsToSelector:`、`instancesRespondToSelector:` 和 `conformsToProtocol:` 有什么区别？

- `[obj respondsToSelector:@selector(run)]`：当前对象能否响应这个 selector。
- `[Dog respondsToSelector:@selector(shared)]`：`Dog` 类对象能否响应，通常检查 `+shared`。
- `[Dog instancesRespondToSelector:@selector(run)]`：Dog 的实例能否响应 `-run`，不必先创建实例。
- `[obj conformsToProtocol:@protocol(P)]`：类及其继承关系是否声明遵守协议 P。

声明遵守协议不等于 Runtime 会逐项验证所有 required 方法已经实现；“协议关系”和“某个 selector 当前能否响应”是两个问题。需要调用某个可选或动态提供的方法时，仍应根据实际语义检查 `respondsToSelector:`。

#### 为什么业务代码应使用公开 Runtime API，而不是复制 objc4 私有结构？

`objc_object`、isa 位域、`cache_t`、`class_rw_t`、相对方法列表和 PAC 处理都曾随架构及系统版本变化。复制某一版私有结构后直接按偏移读写，可能把 32 位相对项当作 64 位指针、绕过签名认证，或在 ro/rw 拆分变化后访问错误地址，最终导致崩溃。

公开 API 会替调用者处理当前实现细节，例如 `class_getName`、`class_getInstanceSize`、`class_copyMethodList`、`class_getSuperclass`、`object_getClass` 和 `method_getImplementation`。学习私有源码是为了理解设计和排查问题，不代表私有字段成为稳定 ABI。

## 所有权与 ARC

#### 关于垃圾回收

垃圾回收除了 iOS/Swift 采用的引用计数（RC）外，还包括标记-清除、标记-整理、分代收集等基于可达性分析的 Tracing GC 算法，RC 胜在实时渐进回收、适合内存紧张的移动端，但天生难以处理循环引用，而 Tracing GC 能正确回收循环引用对象，代价是需要全局暂停扫描（STW）。




#### MRC 的四条所有权规则

1. 通过 `alloc`、`new`、`copy`、`mutableCopy` 方法族取得对象时，调用方拥有返回对象。
2. 对原本不拥有的对象执行 `retain`，可以取得一份自己的所有权。
3. 不再需要自己拥有的对象时，必须通过 `release` 或 `autorelease` 放弃对应所有权。
4. 不能对自己并不拥有的对象执行 `release`。

判断依据是 API 的命名约定，不是方法内部是否真的分配了新对象。不可变对象执行 `copy` 可能直接返回自身，但调用方仍然拥有这个返回值；非创建方法可能返回新对象，但调用方仍然不拥有它。

一次 `release` 只代表放弃自己的一份所有权。只有最后一份所有权也被放弃、引用计数归零，对象才进入销毁流程。Core Foundation 的 Create/Copy Rule 与 Get Rule 遵循同样的思路。

#### MRC 下，一个对象怎样安全地长期保存另一个对象？

只执行 `_name = name` 仅仅复制了指针，没有取得对象所有权。外部释放对象后，`_name` 可能成为野指针。MRC setter 需要保存新对象、放弃旧对象，并处理自赋值：

```objc
- (void)setName:(NSString *)name {
    if (_name != name) {
        [_name release];
        _name = [name retain];
    }
}

- (void)dealloc {
    [_name release];
    [super dealloc];
}
```

`retain` 让所属对象取得新值的一份所有权；`release` 旧值避免原对象泄漏；`_name != name` 防止自赋值时先释放唯一所有者，再对已销毁对象执行 `retain`。所属对象销毁时，还要在 `dealloc` 中释放当前持有的值。

#### `autorelease` 解决什么问题？

不属于 `alloc`、`new`、`copy`、`mutableCopy` 方法族的方法，通常应返回一个调用方不拥有的对象。创建方直接返回自己拥有的对象而不释放会泄漏；返回前立即 `release`，调用方还未使用，对象就可能被销毁。

`autorelease` 用来延后放弃这一份所有权：

```objc
Box *makeBox(void) {
    Box *box = [[Box alloc] init];
    return [box autorelease];
}
```

调用方可以在对象仍有效时使用它；若需要长期保存，应执行 `retain` 取得自己的所有权。池排空时只执行延迟的 `release`，如果还有其他所有者，对象仍会存活。

#### AutoreleasePool 的底层结构和排空过程是什么？

当前 objc4 中，自动释放池可以理解为按页组织的指针栈。条目保存等待接收 `release` 的对象，或保存区分嵌套池的 `POOL_BOUNDARY`。多个 `AutoreleasePoolPage` 通过 `parent`、`child` 形成双向链表，线程本地存储记录当前热页。

`objc_autoreleasePoolPush` 把值为 `nil` 的边界压栈并返回边界位置；`objc_autoreleasePoolPop` 从栈顶向该边界回退，依次向记录的对象发送 `release`。嵌套池有多个边界，每次 pop 只处理对应边界以内的对象。

当前 Runtime 还可能使用空池占位、相邻指针合并和返回值所有权交接等优化，所以“`autorelease` 一定把对象指针写入池页”不是稳定保证。稳定语义只是延后放弃所有权。

主线程通常由 RunLoop observer 管理池：进入循环时建立，在即将休眠时清理并重建，退出时再次清理。长期运行并持续产生临时对象的辅助线程任务，应在合适的循环或任务边界显式使用 `@autoreleasepool` 控制峰值。

#### 引用计数存在哪里？

在支持 non-pointer isa 和内联引用计数的当前实现中，常用计数优先保存在 isa 的 `extra_rc` 字段中。字段装不下时，Runtime 设置 `has_sidetable_rc`，把部分额外计数转移到 SideTable，同时在 isa 中保留一部分计数，使后续常见的 `release` 不必立刻访问 SideTable。

具体位宽取决于架构和 Runtime 版本。文章使用的 objc4 版本中，带指针认证的 arm64 分支以及 arm64 模拟器使用 8 位 `extra_rc`，`RC_HALF` 为 128；无指针认证的 arm64 分支使用 19 位，`RC_HALF` 为 262144。

受控实验中，8 位字段增长到 255 后，下一次 `retain` 使 `has_sidetable_rc` 变为 1，`extra_rc` 回落到 128，另一部分计数进入 SideTable。这个临界点是版本和架构相关的实现细节，不能作为固定规则背诵。

#### 为什么不应该用 `retainCount` 判断对象何时销毁？

`retainCount` 只是某一瞬间、某一实现路径下的观测值，无法完整表达所有权关系：

- 自动释放池里尚未执行的 `release` 不容易从这个数值推导。
- 编译器优化与临时引用会改变观测结果。
- Tagged Pointer 没有独立堆对象本体，可能返回 `INT64_MAX` 等特殊值。
- 常量对象、单例和类簇可能使用特殊实现。
- 即使当前值是 1，也不能推出最后一个所有者何时、在哪个线程释放它。

调试生命周期应该分析所有权关系，使用 `dealloc` 断点、Memory Graph、Allocations、Zombie 或 Address Sanitizer，而不是依赖 `retainCount`。

#### 最后一次 `release` 之后发生什么？

最后一份所有权被放弃后，引用计数归零，Runtime 向对象发送 `dealloc`。随后大致存在两条路径：

```text
快速路径：没有弱引用、关联对象、C++ 析构和 SideTable 状态
        → 直接 free

慢速路径：
        → 执行 .cxx_destruct
        → 移除关联对象
        → clearDeallocating，清空弱引用并处理 SideTable
        → free
```

MRC 中重写 `dealloc` 时，要释放自己拥有的实例变量，并把 `[super dealloc]` 放在最后；不要直接调用对象的 `dealloc`。ARC 中不能手写 `release` 或 `[super dealloc]`，编译器会生成相应清理逻辑。

`dealloc` 在最后一份强引用被释放的线程执行，不能假设它一定发生在主线程。文件描述符、网络连接等需要确定关闭时机的资源，应提供显式生命周期方法，而不是只依赖 `dealloc`。

#### dealloc的流程

当对象的引用计数为0，系统会自动调用dealloc方法，回收内存。最后一次release在哪个线程就在哪个线程调用dealloc。

**内存****释放顺序 是从子类到父类。首先，当前对象的 dealloc 方法会被调用，释放对象的实例变量，然后调用父类的 dealloc，依次向上直到 NSObject 的 dealloc 方法被调用，最后释放对象的内存。


1. NSObject 的 dealloc
当一个对象的引用计数归零时，系统会自动调用它的 `dealloc` 方法。它本身并不做实际的清理工作，而是直接转发调用了 `_objc_rootDealloc(self)`，把释放流程交给 runtime 内部处理。

2. _objc_rootDealloc
这是一个中转函数，把面向 Objective-C 语义的 `dealloc` 调用，转换成面向底层 `objc_object` 结构体的方法调用

3. rootDealloc —— 判断是否走"快速释放"路径

- 如果对象是 Tagged Pointer 类型，那么根本不需要走释放流程，直接 `return`。
- 如果不是 Tagged Pointer，runtime 会检查五个条件是否**同时满足**：

1. 是否是优化过的 isa 指针（nonpointer）；
2. 是否**没有**被弱引用引用过；
3. 是否**没有**关联对象（`objc_setAssociatedObject` 设置的那种）；
4. 是否**没有**自定义的 C++ 析构函数（`has_cxx_dtor`）；
5. 是否**没有**启用 sidetable 保存引用计数。

如果这五个条件都成立，说明这个对象"干净"到不需要任何额外清理，runtime 就会直接调用 `free(this)` 快速释放内存，跳过后续复杂的处理流程。反之，只要有任意一个条件不满足（比如对象被 weak 引用过，或者挂载了关联对象），就必须走 `object_dispose` 这条慢路径。

4. object_dispose

先调用 `objc_destructInstance` 做真正的清理工作，然后再 `free(obj)` 释放内存本体，最后返回 `nil`。它把"清理"和"释放内存"两个步骤明确拆开，保证清理动作完成之后才真正回收内存空间。

#### **4.1 objc_destructInstance —— 三件清理工作**

这个函数负责在释放内存之前做三件事，且执行顺序有讲究（文章特别强调"这个顺序很重要"）：

- 如果对象存在 C++ 成员变量或者遵循 ARC 规则需要清理的实例变量，就调用 `object_cxxDestruct` 执行析构；
- 如果对象存在关联对象（associated objects），就调用 `_object_remove_assocations` 去 AssociationManager 中移除这些关联关系；
- 最后调用 `clearDeallocating()`，清理所有指向自己的弱引用。

之所以要先处理 C++ 析构和关联对象，再处理弱引用清理，是因为析构过程中可能还会访问到对象自身的一些状态，必须在弱引用被清空之前完成。

#### **4.2 clearDeallocating —— weak 指针置 nil 的核心**

这是整条链路里和 `weak` 关键字关系最密切的一环，也是很多面试会追问的细节。它的实现会根据 isa 指针类型走不同路径：如果是老式的裸指针 isa，就直接走 `sidetable_clearDeallocating` 慢速路径；如果是优化过的 nonpointer isa，但存在弱引用记录或者 sidetable 引用计数，也会走 `clearDeallocating_slow`。

这个"慢速清理"背后的具体机制是：runtime 会先从全局的 `SideTables`（一组用于管理引用计数和弱引用的哈希表）中，根据对象地址定位到它所属的 `SideTable`；再从这个 SideTable 内部的 `weak_table` 中，找到记录了"谁在弱引用我"的 `weak_entry_t` 结构；然后遍历这个结构里保存的所有 `referrer`（也就是所有指向该对象的弱引用变量的地址），把它们逐一置为 `nil`；清理完成后，如果这个 `weak_entry_t` 已经没有任何弱引用记录了,就把它从 `weak_table` 中移除。这也正是"weak 指针在对象释放后会自动变成 nil"这一经典特性在底层的真正实现方式——并不是魔法,而是 runtime 主动遍历并清空了所有记录在案的弱引用地址。


#### dealloc释放哪些东西

- 根据条件判断是否有isa、cxx、关联对象、弱引用表、引用计数表，如果没有，则直接free释放内存
    
- 如果有，则进入object_dispose方法
    
- 进入object_dispose源码，其目的有以下几个
    
    - 销毁实例，主要有以下操作

        - 删除关联引用
            
        - 释放散列表
            
        - 清空弱引用表
            
    - free释放内存


#### 野指针、空指针和 悬垂指针

- 空指针值为nil，0，NULL，空指针是一个有效指针，给空指针发送消息是不会报错的（nil对应对象是空的，Nil对应类对象为空）
    
- 野指针：未初始化的指针可能指向任意内存地址。
    
- 悬挂指针：当一个指针指向的内存被释放后，该指针不再有效。如果尝试再次使用它，可能会导致未定义的行为。

#### 实例变量、属性、getter 和 setter 分别是什么？

实例变量（ivar）是对象内部实际保存状态的存储槽位，通常写在类声明、Class Extension 或实现允许的位置中：

```objc
@interface Person : NSObject {
    NSString *_name;
}
@end
```

每个 `Person` 实例都有自己的 `_name`。它属于对象布局的一部分，可以通过 `object_getIvar`、`class_getInstanceVariable` 等 Runtime API 观察。

属性（property）不是另一份数据，也不等同于实例变量。它首先是一对访问方法的声明：

```objc
@property (nonatomic, copy) NSString *name;
```

这条声明描述了：

```objc
- (NSString *)name;
- (void)setName:(NSString *)name;
```

编译器通常会自动合成这两个方法，并生成一个名为 `_name` 的实例变量作为后备存储。但属性也可以使用已有 ivar、计算结果或完全自定义的 getter/setter，所以“属性一定对应一个同名成员变量”并不成立。

点语法也不是直接读写 ivar：

```objc
self.name = value;  // [self setName:value]
id value = self.name; // [self name]

_name = value;      // 直接访问实例变量，绕过 setter
```

因此，自定义 setter 中的所有权逻辑、KVO 通知和副作用，直接写 `_name` 时都不会自动经过。

#### `@property`、`@synthesize` 和 `@dynamic` 

`@property` 声明访问方法以及访问器应采用的语义，例如 `copy`、`strong`、`weak`、`assign`、`readonly`、`nonatomic`。

`@synthesize name = _name;` 要求编译器为属性生成 getter/setter，并使用 `_name` 作为后备实例变量。现代 Objective-C 通常支持自动合成，因此大多数普通属性不需要手写 `@synthesize`。

`@dynamic name;` 表示不要由编译器生成访问器，开发者承诺这些方法会在运行时以其他方式提供，例如 Core Data 的动态属性。如果运行时最终没有对应方法，调用时仍会发生 `unrecognized selector`。

`readonly` 只在当前声明中公开 getter，不公开 setter；可以在 Class Extension 中把同一属性重新声明成 `readwrite`，实现“对外只读、类内可写”。`getter=` 和 `setter=` 可以修改访问器名称，BOOL 属性常见写法是：

```objc
@property (nonatomic, assign, getter=isEnabled) BOOL enabled;
```

#### `@public`、`@protected`、`@private` 和 `@package` 

这些关键字控制的是实例变量的直接访问权限，不是属性 getter/setter 的可见性。

- `@private`：只有声明该 ivar 的类可以直接访问。
- `@protected`：声明类及其子类可以直接访问；这是 ivar 的常见默认权限。
- `@public`：其他代码可以通过 `object->_ivar` 直接访问，会破坏封装，业务代码很少使用。
- `@package`：用于框架或包边界内的访问控制，在普通 App 代码中较少使用。

属性方法能否被调用，主要由方法声明是否对调用方可见以及对象是否响应对应 selector 决定。即使 ivar 是 `@private`，公开的属性 getter/setter 仍然可以正常访问它。

#### `retain`、`assign` 和 `strong` 的 setter 语义有什么区别？

`assign` 是简单赋值。它适合 `NSInteger`、`BOOL`、`CGFloat`、`CGRect` 等标量或值类型：

```objc
@property (nonatomic, assign) NSInteger count;
```

如果把对象指针声明为 `assign`，setter 不会取得所有权，对象销毁后属性也不会自动置 `nil`，因此可能留下悬垂指针。现代 ARC 代码中，非拥有对象关系通常应该使用 `weak`；`assign` 主要留给非对象值。`weak` 和 `assign` 不能视为等价：二者都不延长对象生命周期，但 `weak` 受 Runtime 管理，对象销毁时会安全置 `nil`。

`retain` 是 MRC 时代用来表达对象拥有关系的属性特性。合成 setter 的核心动作是释放旧对象、对新对象发送 `retain`，再保存指针：

```objc
- (void)setObject:(id)object {
    if (_object != object) {
        [_object release];
        _object = [object retain];
    }
}
```

`strong` 是 ARC 的所有权限定语义，表示存储位置对对象保持强引用。赋入新对象时，编译器和 Runtime 保证新值在需要的生命周期内存活，并正确放弃旧值：

```objc
@property (nonatomic, strong) NSObject *object;
```

从“属性会拥有传入对象”这个高层效果看，`retain` 与 `strong` 很接近；但二者所处的语言模型不同。`retain` 直接描述 MRC setter 要做的引用计数操作，`strong` 描述 ARC 下的所有权关系，具体 retain/release 可以被编译器插入、合并或消除。

#### 为什么现代 Objective-C 很少写 `retain`？也很少显式写 `strong` 吗？

现代工程很少写 `retain`，主要是因为 Apple 已经把 ARC 作为默认的内存管理方式。ARC 禁止开发者显式发送 `retain`、`release` 和 `autorelease`，由编译器根据所有权语义生成并优化相应操作。属性也更推荐使用 `strong`、`weak`、`copy` 来表达对象关系，而不是用 `retain` 描述一次具体操作。

```objc
// MRC 风格
@property (nonatomic, retain) NSObject *object;

// ARC 风格
@property (nonatomic, strong) NSObject *object;
```

但不能说现代代码“不怎么使用 strong”。强所有权仍然是对象图中最常见的关系，例如控制器持有服务对象、模型持有其组成对象、数组持有元素。只是有两种情况会让源码里看起来较少出现 `strong`：

1. ARC 下普通对象局部变量和未显式弱化的对象存储通常按强所有权处理，不必在每个局部变量前写 `__strong`。
2. 一些现代 Objective-C 写法会省略属性中的显式 `strong`，依赖编译器的默认所有权推断；不过公开属性中明确写出 `strong` 往往更容易让读者快速理解对象关系。

真正需要避免的不是 `strong` 本身，而是错误的强引用关系。如果两个对象互相强持有，或对象强持有一个捕获自身的 Block，就可能形成循环引用。此时应根据职责把反向关系改为 `weak`，而不是把所有属性都改成不拥有。

## 操作系统基础

#### 进程和线程的区别是什么？和 iOS 多线程模块怎么对应？

**进程**是操作系统资源分配的基本单位，拥有独立的虚拟地址空间、代码、数据、堆、打开的文件描述符和权限。进程间相互隔离，一个进程崩溃通常不会直接影响其他进程。

**线程**是操作系统调度的基本单位，是进程内的一条执行流。同一进程内的多个线程共享进程的地址空间、全局数据、堆和打开的文件，但每个线程有自己独立的栈、程序计数器和寄存器状态。线程间切换比进程间切换开销更小，但线程共享可变状态会带来数据竞争和同步问题。

**和 iOS 多线程模块的对应**：

- iOS App 启动时系统创建主进程，主线程在进程创建时同步创建。
- `pthread_create`、`NSThread` 直接创建新线程。
- GCD 的队列是任务组织抽象，不等于线程。GCD 管理系统级工作线程池，根据队列类型、QoS 和当前负载动态调度任务到可用线程。
- `dispatch_async` 把任务提交到队列，不等于"创建新线程"；串行队列上的多个任务通常复用同一个线程顺序执行。
- RunLoop 是事件循环机制，运行在特定线程上；主线程的 RunLoop 在 `UIApplicationMain` 内启动，子线程需要手动获取并运行 RunLoop。

进程、线程、队列、RunLoop 是四个不同层次的概念，不能混为一谈。

## 计算机网络基础

#### TCP 为什么是可靠字节流？UDP 为什么不是"低级版 TCP"？

**TCP 的可靠性**体现在：

- **有序交付**：TCP 为每个字节分配序列号，接收方按序重组；乱序到达的段会被缓存，等前面的段到齐后再交付给应用层。
- **确认与重传**：接收方返回 ACK 确认；发送方未收到 ACK 则超时重传。
- **流量控制**：接收方通过滑动窗口告知发送方可接收的数据量，防止发送过快导致接收方溢出。
- **拥塞控制**：根据网络状况动态调整发送速率（慢启动、拥塞避免、快速重传、快速恢复），避免网络瘫痪。

**字节流**语义：TCP 不保留应用层消息边界。发送方写入三次数据，接收方可能一次读完，也可能分多次读；应用层需要自己处理粘包/拆包（例如加长度前缀或分隔符）。

**UDP 不是"低级版 TCP"**：

UDP 是**面向数据报**的无连接协议，每个数据报独立传输、独立路由。它不提供可靠性、有序性、流量控制或拥塞控制，但正因如此开销极低、延迟可控。UDP 适合：

- **实时通信**：语音/视频通话，丢几个包可以接受，重传反而增加延迟。
- **广播/多播**：DNS 查询、DHCP、局域网服务发现。
- **自定义可靠性**：QUIC 在 UDP 之上实现了自己的可靠传输、拥塞控制和加密，绕过内核 TCP 栈的限制。

TCP 和 UDP 是针对不同场景设计的传输层协议，不是高低级关系。

#### HTTP 方法的语义是什么？

HTTP 方法定义了客户端对资源的操作意图。常见方法：

- **GET**：请求获取指定资源的表示，应该是安全的（不改变服务器状态）和幂等的（多次请求结果相同）。不应有请求体；查询参数放在 URL。
- **POST**：向指定资源提交数据，通常导致服务器状态变化或副作用（例如创建资源、提交表单）。非幂等：多次 POST 可能创建多个资源。
- **PUT**：用请求体中的表示替换目标资源的全部内容。幂等：多次 PUT 同样内容，结果相同。
- **PATCH**：对资源进行部分修改。幂等性取决于具体实现。
- **DELETE**：删除指定资源。幂等：删除已删除的资源通常返回 404 或 204，但不产生新的副作用。
- **HEAD**：与 GET 相同，但只返回响应头，不返回响应体。用于检查资源是否存在、获取元数据或验证缓存。
- **OPTIONS**：查询服务器支持哪些方法，常用于 CORS 预检请求。

**安全方法**（GET、HEAD、OPTIONS）不应改变服务器状态。**幂等方法**（GET、PUT、DELETE、HEAD、OPTIONS）多次执行结果相同。POST 既不安全也不幂等。

#### HTTP 状态码的分类和常见状态码是什么？

HTTP 状态码分五类：

- **1xx（信息性）**：请求已接收，继续处理。例如 `100 Continue`（客户端应继续发送请求体）、`101 Switching Protocols`（WebSocket 握手）。
- **2xx（成功）**：
  - `200 OK`：请求成功，响应体包含请求的资源。
  - `201 Created`：资源已创建，通常在 POST 后返回，`Location` 头指向新资源 URI。
  - `204 No Content`：请求成功但无响应体，常用于 DELETE 或 PUT。
- **3xx（重定向）**：
  - `301 Moved Permanently`：资源永久移动，浏览器应更新书签，搜索引擎更新索引。
  - `302 Found`：临时重定向，POST 可能被改为 GET（历史行为）。
  - `304 Not Modified`：资源未修改，客户端应使用缓存版本。
  - `307 Temporary Redirect` / `308 Permanent Redirect`：语义更严格的重定向，保证方法和请求体不变。
- **4xx（客户端错误）**：
  - `400 Bad Request`：请求格式错误或无法理解。
  - `401 Unauthorized`：需要身份验证（响应应包含 `WWW-Authenticate` 头）。
  - `403 Forbidden`：服务器理解请求但拒绝授权。
  - `404 Not Found`：资源不存在。
  - `405 Method Not Allowed`：方法不被允许（如对只读资源执行 POST）。
  - `429 Too Many Requests`：请求过于频繁，触发限流。
- **5xx（服务器错误）**：
  - `500 Internal Server Error`：服务器遇到意外情况。
  - `502 Bad Gateway`：网关或代理收到上游无效响应。
  - `503 Service Unavailable`：服务暂时不可用（过载或维护），`Retry-After` 头建议重试时间。

状态码是语义标记，实际行为还需结合响应头和响应体。

#### HTTP 缓存机制和 HTTPS 握手的核心流程是什么？

**HTTP 缓存**通过响应头控制客户端和中间代理是否、如何缓存响应：

- **强缓存**（不发请求直接用缓存）：
  - `Cache-Control: max-age=3600`：缓存 3600 秒内有效，直接使用，不向服务器验证。
  - `Cache-Control: no-store`：禁止缓存。
  - `Cache-Control: no-cache`：可以缓存，但使用前必须向服务器验证（变成协商缓存）。
- **协商缓存**（发请求验证缓存是否仍有效）：
  - 服务器首次响应带 `ETag: "abc123"`（资源指纹）或 `Last-Modified: <时间>`。
  - 客户端再次请求时带 `If-None-Match: "abc123"` 或 `If-Modified-Since: <时间>`。
  - 资源未变返回 `304 Not Modified`（无响应体），客户端继续用缓存；已变返回 `200` 和新内容。

**HTTPS 握手**（TLS 1.2 简化流程）：

1. **Client Hello**：客户端发送支持的 TLS 版本、密码套件列表、随机数 ClientRandom。
2. **Server Hello**：服务器选择 TLS 版本和密码套件，发送随机数 ServerRandom 和服务器证书（包含公钥）。
3. **证书验证**：客户端验证服务器证书链是否可信（签名、有效期、域名匹配）。
4. **密钥交换**：
   - RSA 方式：客户端生成 PreMasterSecret，用服务器公钥加密后发送；服务器用私钥解密。
   - ECDHE 方式（前向保密）：双方交换公开参数，各自计算出共享密钥。
5. **会话密钥生成**：双方用 ClientRandom、ServerRandom 和 PreMasterSecret（或 ECDHE 共享密钥）派生对称加密的会话密钥。
6. **Finished 消息**：双方发送加密的握手完成消息，验证对方正确派生出会话密钥。
7. **应用数据传输**：用对称加密（AES-GCM 等）加密 HTTP 数据，用 HMAC 或 AEAD 保证完整性。

TLS 1.3 简化了握手（1-RTT 或 0-RTT），去除不安全的密码套件，强制前向保密。

## 数据库基础

#### SQL 的 CRUD 基础语法会不会写？

**增（Create）**：
```sql
INSERT INTO users (name, age, email) VALUES ('Alice', 25, 'alice@example.com');
INSERT INTO users (name, age) VALUES ('Bob', 30), ('Charlie', 28);  -- 批量插入
```

**查（Read）**：
```sql
SELECT name, age FROM users WHERE age > 20 ORDER BY age DESC LIMIT 10;
SELECT COUNT(*) FROM users WHERE age >= 18;
SELECT department, AVG(salary) AS avg_salary FROM employees GROUP BY department HAVING AVG(salary) > 50000;
```

**改（Update）**：
```sql
UPDATE users SET age = 26, email = 'alice_new@example.com' WHERE name = 'Alice';
UPDATE products SET stock = stock - 1 WHERE id = 123;  -- 原子递减
```

**删（Delete）**：
```sql
DELETE FROM users WHERE age < 18;
DELETE FROM orders WHERE created_at < '2023-01-01';
```

**事务**：
```sql
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE user_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE user_id = 2;
COMMIT;  -- 或 ROLLBACK
```

#### 事务的 ACID、索引、B+ 树分别解决什么问题？

**ACID** 保证事务的可靠性：

- **A（Atomicity，原子性）**：事务中的所有操作要么全部成功提交，要么全部失败回滚，不会出现部分完成的中间状态。通过 undo log 实现回滚。
- **C（Consistency，一致性）**：事务执行前后，数据库从一个一致状态转到另一个一致状态，不违反约束（外键、唯一索引、CHECK 约束等）。
- **I（Isolation，隔离性）**：多个并发事务之间相互隔离，一个事务的中间状态对其他事务不可见。隔离级别从低到高：读未提交、读已提交、可重复读、串行化。通过锁或 MVCC 实现。
- **D（Durability，持久性）**：事务一旦提交，其修改永久保存，即使系统崩溃也不会丢失。通过 redo log（WAL，预写式日志）实现。

**为什么事务能大幅提升批量写入性能**：

- 无事务时，每次 `INSERT` 可能立即刷盘（`fsync`），磁盘 I/O 成为瓶颈。
- 开启事务后，多次写操作先记录到内存和日志缓冲区，`COMMIT` 时批量刷一次 WAL，再异步刷数据页，大幅减少随机 I/O 次数。
- SQLite 实测：无事务时每秒几十次插入，开事务后每秒可达数万次。

**索引**解决全表扫描性能问题：

- 无索引时，`SELECT * FROM users WHERE email = 'alice@example.com'` 需要扫描全表（O(n)）。
- 在 `email` 列上建索引后，数据库可以通过索引快速定位（O(log n)），再回表获取完整行。
- 代价：索引占用额外存储，插入/更新/删除时需要同步维护索引，略微降低写性能。

**B+ 树**是数据库索引的常见实现：

- **为什么不用二叉搜索树**：树高过高，磁盘 I/O 次数多（每次节点访问可能触发一次随机 I/O）。
- **为什么不用哈希表**：哈希索引只支持等值查询（`WHERE id = 123`），不支持范围查询（`WHERE id > 100 AND id < 200`）和排序。
- **B+ 树优势**：
  - 高扇出（每个节点存储多个键），树高低（百万行数据通常只需 3-4 层），减少磁盘 I/O。
  - 叶子节点通过链表连接，范围查询和顺序扫描高效。
  - 所有数据存在叶子节点，内部节点只存键用于导航，内存利用率高。

iOS 中 SQLite 默认使用 B-Tree（类似 B+ 树）管理表和索引，FMDB、WCDB 都是对 SQLite 的封装。Core Data 底层可选 SQLite 或二进制存储。
