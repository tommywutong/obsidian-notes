# 第一周验收：对象模型与进程内存地图

本次验收对应暑期计划的“模块 1：对象模型与进程内存地图”。回答以稳定概念为主，具体位布局、私有类名和地址只作为当前实现的观察结果。

## 问题一：`id obj = [NSObject new]` 后，局部变量、指针值、对象本体分别在哪里？

### 先给结论

> `obj` 是一个局部指针变量。在 Debug、未优化的直觉模型中，它通常位于当前线程的栈帧；优化后也可能只存在于寄存器中，甚至被消除。`obj` 中保存的值是新建对象的地址；`[NSObject new]` 创建的普通对象本体位于内存分配器管理的堆区域。`&obj` 是指针变量自己的地址，`obj` 是变量里保存的对象地址，二者不是同一个地址。

把这一行拆开：

```objc
id obj = [NSObject new];
```

| 要观察的东西 | 含义 | 通常在哪里 |
| --- | --- | --- |
| `obj` 这个变量 | 一个能够保存 Objective-C 对象引用的局部变量 | Debug、未优化时通常在当前线程栈；优化后可能在寄存器 |
| `obj` 的值 | 普通情况下是对象本体的首地址 | 值本身保存在变量或寄存器中；这个地址指向分配器区域 |
| `&obj` | 局部指针变量自己的地址 | 如果变量有可观察的存储位置，通常位于当前栈帧 |
| 对象本体 | `NSObject` 实例的完整内存 | 分配器管理的可读写堆区域 |

```text
当前线程栈                         分配器管理的堆区域

┌─────────────────┐              ┌──────────────────────┐
│ obj              │              │ NSObject 对象本体     │
│ 保存 0x105d... ──┼─────────────▶│ isa / isa_storage ... │
└─────────────────┘              └──────────────────────┘
  ↑                 
 &obj
```

这里必须分清三个表达式：

```objc
&obj          // 指针变量自己的地址
obj           // 指针变量保存的值，即普通对象地址
*obj          // 概念上是该地址处的对象；业务代码通常不会这样直接解引用 id
```

### 真机实验怎样支持这个结论

在 iPhone 15 的 Debug 实验中，同一个局部指针变量依次指向三个同时存活的 `NSObject`：

- `&object` 一直是 `0x16f138950`，落在线程栈的 `rw-` Region；
- 三次 `object` 分别是 `0x105da0bc0`、`0x105da0bd0`、`0x105da0be0`；
- 三个对象地址落在分配器管理的另一个 `rw-` Region。

实验说明“局部指针变量在栈上”和“普通对象本体在堆中”可以同时成立。地址只属于那一次运行，不能把地址范围和相邻关系背成固定规律。

### 需要主动补充的边界

1. “局部变量一定在栈上”不严谨，编译器可以把它放进寄存器或直接优化掉。
2. `strong`、`weak` 描述所有权或引用语义，不负责决定变量位于栈还是堆。
3. 字符串字面量通常来自只读文件映射，不是每次执行都创建一个普通堆对象。
4. Tagged Pointer 直接把类型和值编码在指针值中，没有它所指向的普通对象本体。
5. `sizeof(obj)` 得到的是指针本身的大小，不是对象本体大小。

### 面试口述版

> `obj` 是局部指针变量，未优化时通常在当前线程栈上；优化后也可能在寄存器。变量里保存的是对象地址，而 `[NSObject new]` 创建的普通对象本体由分配器放在堆区域。`&obj` 看的是变量自己的地址，`obj` 看的是对象地址，不能把变量和对象本体混为一谈。字符串字面量和 Tagged Pointer 是需要另外说明的例外。

## 问题二：实例、类对象、元类之间的 `isa` 与 `superclass` 链怎么走？

假设有下面的继承关系：

```objc
@interface Animal : NSObject
@end

@interface Dog : Animal
@end

Dog *dog = [Dog new];
```

先区分两种关系：

| 关系 | 回答的问题 |
| --- | --- |
| `isa` | 当前这个对象应该去哪个类对象中寻找对应层级的方法 |
| `superclass` | 当前类找不到方法时，继承查找应该继续去哪里 |

### `isa` 链

```text
dog 实例
   │ isa
   ▼
Dog 类对象
   │ isa
   ▼
Dog 元类
   │ isa
   ▼
NSObject 根元类
   │ isa
   └──────────────▶ NSObject 根元类自身
```

- 实例的 `isa` 指向它所属的类对象，实例方法保存在这一层的类数据中。
- 类对象本身也是对象，它的 `isa` 指向对应元类；类方法作为元类的“实例方法”保存在元类中。
- 非根元类的 `isa` 最终指向根元类。
- 根元类的 `isa` 指向自己，形成闭环。

### 普通类的 `superclass` 链

```text
Dog 类
   │ superclass
   ▼
Animal 类
   │ superclass
   ▼
NSObject 类
   │ superclass
   ▼
nil
```

这条链描述普通的类继承关系，也是实例方法向父类继续查找的路径。

### 元类的 `superclass` 链

```text
Dog 元类
   │ superclass
   ▼
Animal 元类
   │ superclass
   ▼
NSObject 根元类
   │ superclass
   ▼
NSObject 类
   │ superclass
   ▼
nil
```

元类的 `superclass` 链让类方法也能继承。根元类的 `superclass` 最后拐回 `NSObject` 类，因此类对象还能获得根类提供的一部分基础对象行为。

### 用 Runtime API 沿图走

```objc
object_getClass(dog);                          // Dog 类
object_getClass(Dog.class);                    // Dog 元类
object_getClass(object_getClass(Dog.class));   // NSObject 根元类

class_getSuperclass(Dog.class);                // Animal 类
class_getSuperclass(object_getClass(Dog.class));
                                                  // Animal 元类
```

可以把两个 API 记成：

```text
object_getClass       沿 isa 关系走一步
class_getSuperclass   沿 superclass 关系走一步
```

但这只是便于读图的记忆方式。`object_getClass` 还要正确处理 Tagged Pointer 等特殊情况，业务代码不要自行读取私有 `isa` 位布局。

### 面试口述版

> 实例的 isa 指向类，类的 isa 指向元类，普通元类的 isa 最终指向根元类，根元类的 isa 指向自己。普通类的 superclass 按 Dog、Animal、NSObject、nil 向上走；元类的 superclass 则按 Dog 元类、Animal 元类、NSObject 根元类向上走，根元类最后再连接到 NSObject 类。isa 解决“去哪个层级找方法”，superclass 解决“当前层找不到后沿继承关系去哪里”。

## 问题三：`isKindOfClass:` 为什么要区分接收者是实例还是类对象？

### 根本原因

Objective-C 同时存在实例方法 `-isKindOfClass:` 和类方法 `+isKindOfClass:`，它们的查找起点不同：

```objc
// 实例接收者：从实例所属的普通类开始
- (BOOL)isKindOfClass:(Class)target {
    for (Class cls = [self class]; cls; cls = class_getSuperclass(cls)) {
        if (cls == target) return YES;
    }
    return NO;
}

// 类对象接收者：从类对象所属的元类开始
+ (BOOL)isKindOfClass:(Class)target {
    for (Class cls = object_getClass(self); cls; cls = class_getSuperclass(cls)) {
        if (cls == target) return YES;
    }
    return NO;
}
```

因此不能只记“`isKindOfClass:` 会沿父类链查找”，还要先问：**它从普通类链开始，还是从元类链开始？**

### 实例作为接收者

```objc
[dog isKindOfClass:Dog.class];       // YES
[dog isKindOfClass:Animal.class];    // YES
[dog isKindOfClass:NSObject.class];  // YES
```

查找路径是：

```text
Dog 类 → Animal 类 → NSObject 类 → nil
```

它问的是：“这个对象是不是目标类或者目标类子类的实例？”

### 类对象作为接收者

```objc
[Dog isKindOfClass:Dog.class];                    // NO
[Dog isKindOfClass:Animal.class];                 // NO
[Dog isKindOfClass:NSObject.class];               // YES
[Dog isKindOfClass:object_getClass(Dog.class)];   // YES
```

查找从 `Dog` 类对象的 `isa`，也就是 `Dog` 元类开始：

```text
Dog 元类 → Animal 元类 → NSObject 根元类 → NSObject 类 → nil
```

所以它不会经过 `Dog 类` 或 `Animal 类`，却会在链尾经过 `NSObject 类`。这就是一些经典 Runtime 判断题看起来反直觉的原因。

### 顺便区分 `isMemberOfClass:`

- `isKindOfClass:` 从起点出发，继续沿 `superclass` 查找。
- `isMemberOfClass:` 只比较起点，不继续找父类。
- 实例方法从普通类开始；类方法从元类开始。

### 面试口述版

> 因为实例对象和类对象属于不同层级。实例调用 `-isKindOfClass:` 时，从实例所属的普通类开始沿 superclass 查找；类对象调用 `+isKindOfClass:` 时，先通过 isa 到元类，再沿元类的 superclass 链查找。所以同一个目标 Class，在实例接收者和类对象接收者上可能得到不同结果。做题前必须先确定 receiver 是实例还是类对象。

## 问题四：Tagged Pointer 为什么能节省一次堆分配？哪些编码细节不能背死？

### 为什么能省掉普通堆对象

普通小对象通常需要这样保存数据：

```text
指针变量
   │ 保存对象地址
   ▼
堆对象本体
   ├── isa
   ├── 对象数据
   └── 引用计数相关状态
```

Tagged Pointer 则把类型标记和小型数据直接编码进一个指针大小的值：

```text
指针变量
   │
   ▼
[ Tagged 标记 | Tag | Payload ]
```

这里的完整位模式不再是普通对象本体的地址，所以不需要为这个小值额外执行一次普通对象的堆分配。

Runtime 收到消息时会先识别 Tagged Pointer，从位模式中取得 Tag，再查询内部类表获得 Class，最后进入正常的方法缓存和方法查找流程：

```text
Tagged Pointer
   ↓ 提取 Tag
Runtime 类表
   ↓
Class
   ↓
方法缓存与方法查找
```

### 它具体省下什么

| 普通小对象 | Tagged Pointer |
| --- | --- |
| 需要普通堆对象分配 | 不需要独立的普通堆对象 |
| 对象中需要 isa 和数据空间 | 类型与值编码在指针位中 |
| 走普通 retain/release 状态维护 | retain/release 走特殊快速路径 |
| 引用计数归零后销毁并释放内存 | 没有独立对象本体需要 `dealloc` |
| 读取时先通过地址访问对象 | 从位模式中解码 Payload |

因此它省下的不只是对象本体的几个字节，还省掉了普通对象的“分配—引用计数—销毁”路径。

### 可以记住的稳定思想

1. Tagged Pointer 把类型信息和小型值编码进一个指针大小的位模式。
2. 它没有可供普通解引用的独立堆对象，也没有对象头中的普通 `isa`。
3. Runtime 可以通过 Tag 查询 Class，所以它仍然能够接收 Objective-C 消息。
4. 值装不下时，Foundation 可以退回普通堆对象。
5. 业务代码应该依赖对象语义，而不是依赖 Tagged Pointer 的私有编码。

### 不能背死的实现细节

以下内容都可能随 CPU 架构、系统版本和 Foundation 实现变化：

- Tagged 标记位究竟在最高位还是最低位；
- Tag、Extended Tag 和 Payload 的具体 bit 范围；
- 某个 Tag 数字具体对应哪个私有类；
- 哪些类、哪些数值范围、多少长度的字符串一定使用 Tagged Pointer；
- 当前进程的 obfuscator 和最终打印出的十六进制位模式；
- `__NSCFNumber`、`NSTaggedPointerString` 等内部类名；
- 某个字面量是否被编译器折叠成常量对象。

当前 arm64 iOS 的源码和实验可以用于理解 Split Tagged Pointer、最高位标记、基础/扩展 Tag 以及混淆过程，但这些属于当前实现，不是业务契约。

### 两个常见误区

1. `malloc_size(value) == 0` 不能单独证明它是 Tagged Pointer；字符串字面量等非 malloc 对象也可能得到 0。
2. 同值的小 `NSNumber` 使用 `==` 可能碰巧相等，但对象值比较仍应使用 `isEqual:`；大值退回两个堆对象后，地址可能不同。

### 面试口述版

> Tagged Pointer 把 Tag 和 Payload 直接编码在一个指针大小的值中，不再额外创建普通堆对象，因此省掉对象本体分配、普通引用计数维护和销毁路径。Runtime 根据 Tag 查类表，仍然能找到 Class 并发送消息。可以记住这个机制，但不能背死标记位、Tag 编号、Payload 宽度、混淆方式以及某个值是否一定 tagged，因为这些都是会随架构和系统版本变化的私有实现。
