# 对象通信研究简报

## 一、`conformsToProtocol:` 的继承链是在 NSObject 层走的

objc4 `NSObject.mm`：

```objc
- (BOOL)conformsToProtocol:(Protocol *)protocol {
    if (!protocol) return NO;
    for (Class tcls = [self class]; tcls; tcls = tcls->getSuperclass()) {
        if (class_conformsToProtocol(tcls, protocol)) return YES;
    }
    return NO;
}
```

**最容易写错的点：继承链是这个 for 循环走的，不是 `class_conformsToProtocol` 自己走的。** `class_conformsToProtocol` 只看 cls 自己的 protocol 列表，不走 superclass；但对每个 protocol 会递归查父 protocol。

`protocol_conformsToProtocol_nolock` 是**按 mangledName 字符串比较**而不是纯指针比较，因为同名 protocol 可能有多份定义。

## 二、`protocol_t` 的字段顺序

```c
struct protocol_t : objc_object {
    const char *mangledName;
    struct protocol_list_t *protocols;
    method_list_t *instanceMethods;
    method_list_t *classMethods;
    method_list_t *optionalInstanceMethods;
    method_list_t *optionalClassMethods;
    property_list_t *instanceProperties;
    uint32_t size;
    uint32_t flags;
    // 以下字段在磁盘上不一定存在
    const char **_extendedMethodTypes;
    const char *_demangledName;
    property_list_t *_classProperties;
};
```

两点：required 和 optional 是**四张独立的方法列表**（不是 required 全在前）；尾部三个字段靠 `size` + `HAS_FIELD` 宏做版本兼容，老编译器产物里可能根本没有，必须先 `hasXxxField()` 再读。

`getProtocolMethodList` 是 `@required` / `@optional` 分表的直接证据：

```c
if (required) {
    mlistp = instance ? &proto->instanceMethods : &proto->classMethods;
} else {
    mlistp = instance ? &proto->optionalInstanceMethods : &proto->optionalClassMethods;
}
```

`protocol_copyMethodDescriptionList` 头文件 @note：**"Methods in other protocols adopted by this protocol are not included."**
对比 `protocol_getMethodDescription` 的 @note：**"This function recursively searches any protocols that this protocol conforms to."**
一个不递归一个递归，可以写成对比。

## 三、UIControl 的 target 语义 —— 文档只说 "does not retain"

`addTarget(_:action:for:)` 官方 Discussion：

> The control **does not retain** the object in the target parameter. It is your responsibility to maintain a strong reference to the target object while it is attached to a control.

> If you specify `nil`, UIKit searches the responder chain for an object that responds to the specified action message.

`UIControl.h` 头文件更直白：

```
// passing in nil as the target goes up the responder chain. The action may optionally include
// the sender and the event in that order. the action cannot be NULL. Note that the target is not retained.
```

**措辞陷阱：文档只说 "does not retain"，全篇没有 weak / zeroing 字样。** 实测到的 `_target` 置 `0x0` 属于实现细节，文档没有背书，写文章要标成"实测行为，非契约"。

强对照证据 —— AppKit 把 weak 写进了公开头文件，正好衬托 UIKit 的沉默：

```objc
// NSControl.h
@property (nullable, weak) id target; // Target is weak for zeroing-weak compatible objects
                                      // in apps linked on 10.10 or later. Otherwise 'assign'.
```

另两个 target 语义：
- **NSTimer**：*"The timer maintains a strong reference to this object until it (the timer) is invalidated."* userInfo 同样强引用
- **UIGestureRecognizer**：**Apple 对它的 target 持有语义只字未提**（Discussion 和两个 param 都通读过，确实没有）

## 四、UIControl 怎么决定传几个参数 —— 结论和流行说法相反

**没有任何一手证据说明 UIKit 是靠数冒号 / `methodSignature.numberOfArguments` 判断的。**

`sendAction(_:to:from:for:)` 官方 Discussion：

> **By default, this method pushes two parameters when calling the target.** These last two parameters are optional for the receiver because it is up to the caller (usually a UIControl object) to remove any parameters it added. This design enables the action selector to be one of the following:
> - `-(void)action`
> - `-(void)action:(id)sender`
> - `-(void)action:(id)sender forEvent:(UIEvent *)event`

正确解释：`objc_msgSend(target, action, sender, event)` 永远按四个参数发（含 self/_cmd），callee 声明 0/1/2 个参数都能跑，因为 arm64 上多余的实参躺在 x2/x3 里没人读。文档里 "remove any parameters it added" 是 i386 caller-cleanup cdecl 年代留下的措辞。

**这是调用约定层面的技巧，不是运行时的参数计数。**"数冒号"只能写成"自己实现 target-action 时的推荐做法"，不能说成 UIKit 的实现。

## 五、通知中心

### iOS 9 起 selector 版观察者不用手动移除 —— 边界分四类

出自 Foundation Release Notes for OS X 10.11 and iOS 9：

- **适用**：selector 版观察者。能 weak 的存 zeroing weak，不能 weak 的存 "non-weak zeroing reference"，两者都享受 lazy cleanup
- **不适用**：block 版。原文理由 *"since the system still holds a strong reference to these observers"*
- **不适用**：`CFNotificationCenterAddObserver`，原文 *"does not conform to this behavior since the observer may not be an object"*
- **dealloc 期间行为按存储方式分叉**：能 weak 的不再收到；non-weak zeroing 的仍会收到

### 同步派发与 posting thread

两句都出自**归档文档** *Notification Centers*。**现行的 `documentation/foundation/notificationcenter` 页面已经删除了这两句**，`post(name:object:userInfo:)` 页面没有 Discussion 段。引用时必须标注 archive 来源。

流传的那句 `"...synchronously... in the same thread that posts the notification"` 是**两句话拼接改写**的产物，Apple 原文没有任何一句同时包含这两半。加引号引用会失准，须拆成两句分别引。

### `queue:` 参数

> The operation queue where the `block` runs. **When `nil`, the block runs synchronously on the posting thread.**

一个反直觉的点：swift-corelibs-foundation 源码显示，**传了非 nil queue 后仍会阻塞 poster**（`queue.addOperation` 后紧跟 `queue.waitUntilAllOperationsAreFinished()`，带注释 `// Not entirely safe, but maintained for compatibility`）；`queue == current` 时直接同步调用不入队。即"传了 queue 就变非阻塞"在 corelibs 上不成立。**Darwin 真机行为官方未明说，未经一手验证。**

## 六、KVO 补充（来自另一份研究）

- **`KVOImplementation.html` 全页从头到尾没有出现过 `NSKVONotifying_` 一次**，官方措辞只是 "an intermediate class"。这个类名是社区从 runtime 反射观测出来的未文档化细节，不能当官方说法引用
- 官方原话：*"You should never rely on the `isa` pointer to determine class membership. Instead, you should use the `class` method"*
- context 的论证：*"may cause problems for an object whose superclass is also observing the same key path for different reasons"*，推荐 *"The address of a uniquely named static variable within your class makes a good context"*
- **iOS 11 的放宽被社区过度概括**：Foundation Release Notes for macOS 10.13 and iOS 11 的 "Relaxed Key-Value Observing Unregistration Requirements" 只解决"被观察对象 dealloc 后残留注册"，且明确排除 `+automaticallyNotifiesObserversForKey:` 返回 NO 的对象。**观察者提前释放导致的野指针崩溃、重复 remove 的 NSRangeException，一个都没解决**

## 七、明说没查到的

- UIKit 不开源，target-action 部分除文档和头文件外没有源码级证据
- Apple 对 `UIGestureRecognizer` 的 target 持有语义没有任何书面说明
- Darwin 上非 nil queue 是否阻塞 poster —— 未验证
- `CFNotificationCenter.c` 从未开源，"三张表出自早期 CF"这个说法**无一手证据**
